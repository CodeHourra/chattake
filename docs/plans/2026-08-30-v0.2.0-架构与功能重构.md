# 寻迹 v0.2.0 架构与功能重构

> 状态：实现与验收完成
> 日期：2026-08-30  
> 基线：`release/v0.1.7`

## 1. 目标与边界

v0.2.0 将寻迹收敛为一个可靠的本地知识闭环：从 Claude Code、Cursor、Codex、CodeBuddy 增量采集会话，经用户确认后调用指定 API 供应商分析，将原子知识发布或送入草稿，并可通过桌面端和只读 MCP 检索。

本版本保持 Vue 3 + Tauri/Rust + SQLite + Bun Sidecar 的本地单体架构，不引入微服务、消息队列、向量数据库、REST API、后台守护进程或模型并发。删除 LLM CLI、所有 `*-internal` 路径和未实现的分类树、Memory、Skill 预留。

## 2. 目标架构

```text
Vue Desktop UI
  ├─ 会话 / 知识 / 草稿 / 设置
  └─ 任务中心（订阅 job://updated）
                  │ Tauri commands + events
Tauri / Rust
  ├─ CollectorScheduler：四来源增量采集
  ├─ JobRunner：持久队列、取消、重试、恢复
  ├─ AnalysisPipeline：内容准备、价值判断、知识提取
  └─ Database：单写连接 + 短生命周期只读连接
          │                         │ JSON-RPC/stdin
       SQLite WAL              Bun Sidecar
          │                         └─ OpenAI-compatible HTTP
          └─ xunji-mcp（独立只读连接、stdio）
```

Sidecar 只负责模型请求、响应解析和错误归类。Rust 负责任务生命周期、业务校验和原子入库。MCP 不复用桌面进程，直接只读打开同一 SQLite。

## 3. 多供应商配置

Distiller 使用“多配置、单激活”模型：

```toml
[distiller]
active_profile_id = "siliconflow-main"

[[distiller.profiles]]
id = "siliconflow-main"
name = "硅基流动"
provider = "siliconflow"
base_url = "https://api.siliconflow.cn/v1"
api_key = "sk-..."
model = "deepseek-ai/DeepSeek-V3"
timeout_secs = 120
```

内置预设包括 OpenAI、DeepSeek、Moonshot、智谱、硅基流动和自定义 OpenAI-compatible。预设只提供默认 Base URL，不固化模型列表。设置页可通过 `GET {base_url}/models` 临时加载模型，失败时仍允许手工填写完整模型 ID。

每个分析任务保存 `profile_id/provider/base_url/model` 快照，分析审计仅保存 Base URL 主机名。API Key 只从配置读入内存，不进入数据库、事件、日志或 MCP。任务失败不会自动切换供应商；用户可选择其他配置重试。

## 4. 数据模型

v0.2.0 重建数据库。旧库先通过 `VACUUM INTO` 备份到 `~/.xunji/db/backups/`，备份失败必须中止重建。

| 表 | 职责 |
|---|---|
| `sessions` | 来源会话、文件指纹、内容哈希、分析状态 |
| `messages` | 标准化消息，按 `(session_id, seq_order)` 索引 |
| `cards` | 0–N 个原子知识项，区分 `published/draft` |
| `tags` / `card_tags` | 主题与技术项的规范化多对多关系 |
| `jobs` / `job_items` | 同步、分析任务及单项状态 |
| `analysis_runs` | Prompt、供应商、模型、Token、耗时与错误审计 |
| `cards_fts` | 知识全文索引；桌面默认检索和 MCP 查询强制发布态过滤 |

会话唯一键为 `(source_id, external_session_id, source_host)`。卡片类型固定为 `decision`、`troubleshooting`、`implementation`、`explanation`、`snippet`，未知值由业务校验或数据库约束拒绝。标签 `kind` 固定为 `topic` 或 `technology`。

## 5. 采集与任务

采集先比较 `mtime + size`，有变化才解析并计算内容哈希。消息数相同但内容变化、消息减少都属于更新。单个会话的元数据与消息在一个事务内替换。

Codex 扫描 `~/.codex/sessions/**/*.jsonl` 与 `~/.codex/archived_sessions/*.jsonl`。仅采集 `response_item` 中 `payload.type=message`、角色为 `user/assistant` 的 `input_text/output_text`；排除 developer、reasoning、工具调用和重复 event 消息。

任务状态为 `queued/running/succeeded/failed/cancelled/interrupted`。启动时自动扫描但不自动分析。异常退出的分析任务改为 `interrupted`，由用户决定是否继续；当前模型调用取消时终止 Sidecar，下一项按需重启。

## 6. 知识提取协议

一场会话只预处理一次，默认输入预算 24,000 字符，完整保留首尾轮次并均匀抽取中间完整轮次。

1. `judge_value` 仅返回 `value + reason`。
2. `high` 进入完整提取并自动发布；`medium` 进入完整提取并保存草稿；`low/none` 不生成知识。
3. `extract_knowledge` 返回 1–3 项，每项包含标题、固定类型、摘要、Markdown 正文、最多 3 个主题标签和最多 5 个技术项。
4. 重新分析始终先生成草稿，旧知识在新结果成功并经用户处理前保持不变。

## 7. 检索与 MCP

FTS5 使用 trigram 支持中英文子串，少于 3 字符时回退到参数化 `LIKE`。默认只检索 `published` 卡片；草稿在桌面端独立查看。

MCP 为只读 stdio Server，提供：

- `xunji_search`
- `xunji_get_card`
- `xunji_list_facets`
- `xunji_get_source`

MCP 不返回草稿、任务、API Key、供应商配置或完整 Base URL。

## 8. 性能与验收基线

- 未变化的第二次同步不重新解析源文件。
- 会话列表不再为每行执行多组相关子查询。
- 对话详情按游标每次加载 100 条消息。
- 所有前端生产 Chunk 低于 500 KB。
- 单写连接保证一致性，列表、搜索和详情使用短生命周期只读连接；在出现实测争用前不引入连接池。
